# EVAL_DESIGN

Date: 2026-11-20. Preregistered: the thresholds and test list below change only by a new, labelled revision, with old results kept.

## Headline claims and how an expert would test them
Shaida makes security claims, not accuracy claims. The field's standard for ZK applications is **soundness, completeness and zero-knowledge**, tested with negative witnesses (inputs that must fail), plus contract-level adversarial tests. We follow that.

| Claim | Standard test | Pass condition |
|---|---|---|
| C1 Soundness: a proof can't overstate vouched income | Negative witnesses for every cheating route (table below) | 100% of cheating cases rejected, by circuit or verifier, with a named reason |
| C2 Completeness: honest proofs verify | Generated honest cases across N = 1…max payments (max 32: bundles of up to 8 proofs of 4, rev. 3), amounts at range edges | 100% verify |
| C3 Disclosure is minimal | Inspect the public signals | Only: bound X, count N, block range, reader, expiry, recipient key, payer set root (plus payer names only if the user opts in). Rev. 3: a bundle of k > 1 proofs also shows each proof's sub-bound, sub-count and sub-range (D12) |
| C4 Aevum-native | Run the full loop on chain 44005 | Every step has a tx hash on explorer-test.qday.info |
| C5 Usable | Proving time in a mid-range laptop browser | Rev. 3: ≤ 30 s per 4-slot proof; a period of N payments needs ⌈N/4⌉ proofs (target; record the real number either way). Rev. 2 target was ≤ 30 s for N ≤ 8 in one proof |

## Cheating cases (C1), each a named test
| ID | Attack | Expected refusal |
|---|---|---|
| X01 | Self-payment from an unregistered wallet | on-chain `PayerNotRegistered` (no V leaf can exist) |
| X02 | Relayed vouch signed by an unregistered address | on-chain `PayerNotRegistered` |
| X03 | Payer revoked, then tries to vouch | on-chain `PayerRevoked` (earlier vouches still count, by design: D3) |
| X04 | Same note counted twice | circuit: duplicate commitment |
| X05 | Note outside the block range | circuit: leaf index out of range |
| X06 | Amount inflated in the witness | circuit: commitment mismatch |
| X07 | Note not in the tree (fabricated commitment) | circuit: Merkle root mismatch |
| X08 | Unswept note (payer could claw back) | circuit: no S leaf in the ledger tree |
| X09 | Payer presents the recipient's income | circuit: payer can't open the sweep note Cs |
| X10 | Expired proof | `ProofExpired` |
| X11 | Wrong reader | `WrongReader` |
| X12 | Replay of a proof for another bound X | public-signal mismatch |
| X14 | Bundle: two proofs whose leaf ranges overlap | verifier `RangesOverlap` |
| X15 | Bundle: the same proof included twice | verifier `RangesOverlap` |
| X16 | Bundle: proofs made for two readers joined | verifier `MixedContexts` |
| X17 | Bundle: proofs with two expiries joined | verifier `MixedContexts` |
| X13 | Cycling: one tUSD8 amount paid, swept, re-paid 3× by the same registered payer | **Counts** (by design, it's real vouched payment). Documented in LIMITS as collusion risk, not a bug. |

## Data
No synthetic "benchmark" we could tune. The test data is produced by real flows on a local Aevum-rules chain and a fork of Aevum with real tUSD8. The final run happens on Aevum Testnet. Honest and cheating witnesses are generated by scripts committed before the circuit is finalised.

## Ceiling / baseline
- Baseline: Gloam's existing `receipt` proof (one payment ≥ X, no payer, no range).
- Ablation: run X01, X05 and X08 against the baseline. They must **pass** there, which shows the new circuit is what stops them.

## End-to-end early
By 2026-11-24, crude but real: deposit → pay → sweep → prove → verify on a fork, with one evidence file.
